# 一次买够最终版实现设计说明

## 1. 总体架构

项目采用前后端分离架构：

- 后端使用 FastAPI 提供 REST API、WebSocket、任务调度和静态上传文件访问。
- 用户端使用 React + TypeScript + Ant Design 5 实现商城、社区、订单、客服和 AI 助手页面。
- 管理端使用 React + TypeScript + Ant Design 5 实现平台后台、商家后台和商家入驻页面。
- 数据库使用 MySQL 8.x，ORM 使用 SQLAlchemy async。
- 异步任务使用 Celery，主要用于订单超时、优惠券过期、自动确认收货等周期任务。
- 支付接入支付宝沙箱扫码支付。

## 2. 后端分层

后端目录以职责分层：

- `app/api/v1/`：HTTP 路由，负责参数接收、鉴权和调用 service。
- `app/models/`：SQLAlchemy ORM 模型。
- `app/schemas/`：Pydantic 请求和响应模型。
- `app/services/`：业务逻辑、事务边界、状态流转和跨模块协作。
- `app/core/`：配置、安全、响应、日志等公共能力。
- `app/db/`：数据库和 Redis 连接。
- `app/tasks/`：Celery 任务。
- `app/websocket/`：WebSocket 连接管理。
- `app/utils/`：分页、格式化、通用工具。

后端设计原则是 router 尽量轻，核心规则放在 service 层。订单、支付、售后、积分、促销、库存等关键状态变化都应由 service 统一处理。

## 3. 前端分层

两个前端工程均采用 Vite + React + TypeScript：

- `src/pages/`：页面级模块。
- `src/components/`：可复用组件。
- `src/services/`：API 请求封装。
- `src/routes/`：路由定义和权限控制。
- `src/utils/`：金额、图片、状态、日期等格式化函数。
- `src/styles/`：全局样式和主题覆盖。

用户端页面围绕真实商城路径组织：首页、商品详情、购物车、结算、订单、订单详情、社区、用户中心、店铺主页、客服和 AI 助手。管理端按平台后台和商家后台拆分路由，避免权限和登录态混用。

## 4. 认证与权限

系统区分普通用户和后台管理员：

- 普通用户使用用户端登录态。
- 平台运营使用平台后台登录态。
- 商家运营使用商家后台登录态。

管理端允许平台账号和商家账号同时登录，token 使用不同 localStorage key 保存。后端通过账号类型、角色和店铺归属控制权限。商家接口必须校验当前商家只能访问本店数据，平台接口处理全局数据。

## 5. 核心业务设计

### 商家入驻

商家账号先提交入驻申请。审核通过后，系统创建店铺并把账号升级为商家运营。审核前账号可登录但不能管理商品和订单。

### 商品与库存

商品由商家创建，平台只做监管。商品包含基础信息、分类、图片、详情图、SKU、价格、划线价、库存和标签。用户端展示商品卡片、商品详情和店铺主页；管理端提供商品维护和监管入口。

### 购物车与订单

购物车按店铺分组，支持勾选和数量修改。提交订单时按店铺拆分为多张订单，并共用一个支付单。订单状态围绕待支付、待发货、待收货、已完成、售后等流程流转。

### 支付

支付单记录支付渠道、金额、支付宝交易号、二维码、支付状态和关联订单。前端生成二维码时锁定按钮，避免重复预创建导致旧二维码失效。支付结果以后端主动查询或支付宝通知同步为准。

### 促销与积分

促销分为优惠券和满减。普通订单最多选择一种满减和一张优惠券，计算顺序为商品价、满减、优惠券、积分抵扣、支付宝支付。积分通过统一积分服务变更，保留流水记录。

### 拼团

商家为本店 SKU 配置拼团活动。用户可开团或参团，拼团订单直接从商品详情或拼团专区进入结算，不进入购物车。拼团成功后订单进入商家发货流程。

### 社区与种草

社区帖子支持分区、话题、图片、评论、点赞、收藏和关联商品。种草帖要求绑定已购商品。用户从种草帖进入商品详情并加购后，购物车和订单保留来源，确认收货后发放积分奖励。

### 售后

售后以订单明细为单位，可按购买数量申请。商家和平台可查看售后详情、凭证和处理结果。单件商品按单件全额退款规则处理。

### 客服

客服会话支持平台咨询和商家咨询。商品详情和订单详情可直接打开对应客服弹窗。平台后台处理平台咨询，商家后台处理本店咨询。新会话自动生成一次欢迎语。

### 报表

报表以现有业务表为数据来源，提供平台全局和商家本店两个视角。前端用图表呈现成交趋势、订单状态、售后分布、排行、促销和社区互动。

### AI 助手

AI 助手通过后端统一接口调用 qwen-flash。当前使用预设系统提示词解释商城功能和流程，后续可扩展为只读查询和客服回复草稿；订单、支付、库存、积分等关键状态继续由原业务接口处理。

## 6. 数据库与配置

项目默认使用 MySQL。`.env` 保存数据库、JWT、Redis、支付宝、AI 模型等配置。开发环境通过 ORM `create_all` 建表；数据库本身由 `backend/scripts/init_mysql_db.py` 创建。分类等业务数据由平台后台配置，不随建库自动写入。

上传文件统一写入 `backend/uploads`，通过静态路径访问。

## 7. 接口规范

接口统一使用 `/api/v1` 前缀，管理端接口使用 `/api/v1/admin` 前缀。响应结构统一为：

```json
{ "code": 0, "message": "ok", "data": {} }
```

分页统一使用 `page`、`page_size`、`total` 和 `list`。金额字段后端统一使用分，字段名以 `_cent` 结尾；前端展示时转换为元。

## 8. 可扩展点

- AI 助手可扩展为读取公开商品、店铺、促销、订单状态和客服会话。
- 报表可扩展更多时间维度、导出字段和运营指标。
- Celery 可扩展更多定时任务，如活动状态刷新、消息通知、数据汇总。
- WebSocket 可扩展客服已读状态、图片消息和通知中心。
- 数据库模型稳定后可引入 Alembic 做正式迁移管理。
