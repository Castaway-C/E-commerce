# 后续迭代路线图

当前用户端、平台端、商家端主要功能已经前后端完整实现，用户端 AI 购物助手最小版已接入 qwen-flash。后续路线不再以“补齐商城基础链路”为目标，而是围绕 AI 助手业务能力、验收硬化、展示质量和测试覆盖推进。

`需求规格说明书.md` 和 `实现设计说明书.md` 是早期历史资料，后续不再作为主要编码依据；以当前代码、接口文档、`docs/handoff.md`、`docs/dev-setup.md` 和 `AGENTS.md` 为准。

## 开发交付标准

每个后续功能至少同时完成：

- 后端：模型、schema、service、router、权限判断、错误码和关键测试。
- 前端：可发现的菜单、页面、表单、列表、状态提示和接口调用。
- 文档：同步更新 `docs/api/*.md`、`docs/dev-setup.md`、`docs/handoff.md`、`AGENTS.md` 或本文。
- 验收：给出可手工走通的流程，重要状态和异常有测试或说明。

除非负责人明确要求，否则不要只新增后端接口而不接前端，也不要只做页面静态占位。

## 当前完成基线

- 用户、平台、商家账号与 token 分离。
- 商家自助入驻、平台审核、店铺自动创建。
- 分类、商品、SKU、图片、图文详情、库存、店铺主页、收藏、关注。
- 购物车、跨店订单、支付宝沙箱扫码支付、发货、确认收货、评价。
- 优惠券、满减、积分抵扣、积分流水和会员配置。
- 售后按订单明细和数量处理，商家和平台可查看详情、凭证并处理售后。
- 社区分区、帖子、评论、点赞、收藏、话题、用户主页、关联商品卡片、内容隐藏。
- 种草来源加购与确认收货后的双向积分奖励。
- 拼团链路：商家配置、用户开团/参团、支付宝支付、成团后进入待发货。
- 平台端和商家端报表看板。
- 用户、平台、商家客服会话，含 HTTP 兜底发送和基础 WebSocket 推送；用户中心客服板块、商品/订单弹窗客服、平台/商家客服工作台均已接入。
- 用户端、平台端、商家端均已拆为正式路由页面。

## 1. AI 助手

用户端悬浮 AI 购物助手最小版已完成，当前通过 `POST /api/v1/ai-assistant/chat` 调用后端。后端优先调用 qwen-flash 的 OpenAI 兼容接口；配置 `DASHSCOPE_API_KEY` 或 `AI_ASSISTANT_API_KEY` 后启用，未配置或调用失败时降级为预设回复。当前不读取实时业务数据。

后续推荐分两步做：

- 用户端悬浮购物助手：逐步基于当前商品、店铺、促销、拼团、社区和订单接口，回答选购、优惠、售后流程、订单状态等问题。
- 客服建议回复：在平台端和商家端客服会话里生成回复草稿，由人工确认后发送。

建议接口形态：

- `POST /api/v1/ai-assistant/chat`：用户端购物助手，当前已实现最小版。
- `POST /api/v1/admin/ai/customer-service/suggest-reply`：平台或商家客服建议回复。
- `GET /api/v1/ai/assistant/capabilities`：前端读取助手能力开关，便于无模型配置时隐藏入口或降级。

安全边界：

- AI 不直接修改订单、支付、退款、库存、积分、优惠券、商品上下架等关键业务状态。
- AI 只读数据时必须沿用当前登录态权限，不能越权读取平台或其它商家的数据。
- 涉及支付、退款、售后争议时，AI 只做解释和引导，最终操作由用户、商家或平台运营确认。
- 模型 API Key 不提交仓库，只放 `.env`。

## 2. 当前问题修复计划

本节记录 2026-07-08 新发现的体验与业务完善项。优先按“公共浏览 -> 结算支付 -> 订单详情 -> 客服 -> 运营配置”的顺序推进。

### A. 公共浏览与商城主页

- 用户端商城首页、商品详情、店铺主页、拼团专区、社区应允许游客浏览。
- 加入购物车、收藏、关注、领取优惠券、进入个人中心、结算、发帖、评论、联系客服等私有操作再提示登录并跳转登录页，登录后尽量回到原页面。
- 商城主页轮播图已实现：平台端 `/admin/home-banners` 可上传宣传图、设置标题/副标题、排序、启停并跳转商品或链接；用户端首页通过 `/home/banners` 展示启用轮播图。
- 首页分类目录已从大块目录改为紧凑胶囊筛选：默认展示一级分类，选中父级后逐级展开子分类，父级分类筛选仍包含全部子孙分类商品，用户端不展示分类 ID。

### B. 商品详情与购物体验

- 商品详情页不重复展示商品轮播图；详情区只展示文字介绍和商家上传的详情图片。
- 评论区放在商品基本信息和图文详情之间，默认只展示少量评价，点击“查看全部”再展开。
- 订单结算页商品明细应像购物车一样展示商品图片。
- 拼团结算页“新增地址”按钮必须实际创建地址并自动选中。

### C. 结算、支付与订单

- 结算页应完成支付全流程：提交订单后留在结算页展示支付单、自动生成支付宝二维码，并提供同步支付结果；不再强制跳到订单页完成支付。
- 用户点击支付后自动开始生成二维码，生成期间锁定按钮，避免重复预创建导致旧二维码过期。
- 支付同步成功后自动跳转订单页；订单页后续补订单详情入口。
- 未支付订单打开订单详情后，应提供“继续支付”并跳回订单结算/支付流程，这是订单详情页开发的一部分。
- 排查支付宝沙箱卡顿或失败：重点检查重复预创建、支付单缓存、前端超时提示、后端网关错误日志和沙箱交易查询延迟。
- 订单页已增加独立订单详情页 `/orders/:orderId`，展示订单流转、物流公司和单号、优惠信息、收货地址、支付单信息和商品明细，并提供评价商品、申请售后、商家客服和平台客服入口；后续可继续深化售后明细聚合、退款联动说明和未支付订单从详情回到结算页的流程复用。

### D. 客服体验

- 商品详情页已支持右下角商家客服弹窗：点击“联系商家”会创建或复用当前商品店铺会话，并可直接查看历史消息、发送文字消息，不再强制跳转客服中心。
- 订单详情页已支持右下角客服弹窗，分为“联系商家客服”和“联系平台客服”，会自动关联当前订单；订单列表只保留查看详情入口。
- 用户中心已新增客服消息板块，复用完整客服面板；`/customer-service` 保留为兼容页，负责会话列表、平台客服、历史会话管理和基础 WebSocket 推送。
- 平台端和商家端客服会话已改为双栏工作台，移除开发调试日志和提示；状态显示使用“进行中/已结束”，结束操作使用“结束”。
- 用户首次创建客服会话时，后端会自动发送一次欢迎语；商家欢迎语使用店名，平台欢迎语使用“一次买够”平台名，暂不提供后台编辑。
- 后续可把弹窗客服升级为 WebSocket 实时接收、支持图片消息和已读状态。

### E. 管理端与运营配置

- 商家发货区域明确提供快递公司和快递单号输入，尽管不实现真实物流轨迹。
- 报表后端暂不大幅扩展，优先复用现有数据做更丰富的数据可视化；当前平台/商家看板已包含成交趋势、订单状态、售后状态、促销漏斗、商品排行、商家排行和社区互动雷达。
- 后续报表可按需要小步增加时间范围、会员积分指标、导出字段和图表说明，保持平台全局与商家本店数据隔离。
- 平台会员积分福利配置已支持不同会员等级每日签到额外积分、每单积分抵扣上限覆盖、积分倍率预留字段和会员权益说明；其中签到加成与等级抵扣上限已参与实际计算，积分倍率当前用于展示和后续积分发放扩展预留。
- 持续清理 UI 和提示中的测试开发术语，尤其是客服、积分流水、接口返回、调试标签等位置。

## 3. 全链路验收与测试补强

重点补以下边界：

- 跨店订单：多店商品、平台券、商家券、平台满减、商家满减、积分抵扣的分摊和退款。
- 支付：重复生成二维码、重复同步、异步通知幂等、支付超时取消。
- 售后：部分数量退款、退款后库存/积分/优惠券/订单状态联动。
- 拼团：多人参团、超时失败、库存回补、积分回退。
- 客服：平台不查看商家会话、商家不查看平台会话、用户只能查看自己的会话；订单详情的商家客服和平台客服入口必须分别进入正确目标会话。
- 报表：平台全局数据与商家本店数据隔离。
- 社区种草：来源加购、普通帖不奖励、商家动态不奖励、确认收货后奖励。

## 4. 页面与展示优化

当前页面已能承载验收，后续可按展示需要继续优化：

- 统一视觉风格、空状态、加载态、错误提示和表单校验。
- 优化报表筛选、导出、图表说明和空状态；新增图表时优先复用已有接口数据，确需新增后端指标时再扩展接口。
- 优化用户中心、订单售后、客服消息和社区详情的可读性。
- 优化移动端适配；当前主要面向 PC 展示。

## 5. 基础设施

- 当前开发环境主要依赖 ORM `create_all` 和 SQLite 补列逻辑，模型稳定后可逐步补 Alembic 迁移。
- Redis 可继续用于 Celery、token 黑名单、热点缓存和消息通知扩展。
- Celery 任务需要保持幂等、日志和失败重试。
- 上传接口可按业务场景继续补文件类型、大小限制和清理策略。
